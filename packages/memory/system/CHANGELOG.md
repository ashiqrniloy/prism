# Changelog

## [Unreleased]

- **STM no longer fails a pass on the tool-call limits, and a backlog splits into trigger-sized passes (plan 217 Task 6).** A gate M-1 smoke run found the STM worker recording 30 to 50 events per batch of conversation. The 33rd call in one turn threw `exceeds 32 tool calls per turn`, which discarded every event of the pass, left coverage in place and sent a larger batch next time. STM now runs the worker loop with `onToolCallLimit: "refuse"`: calls past `worker.maxToolCallsPerTurn` are answered with a `tool_call_limit` error and repeated by the model next turn, and past `worker.maxToolCalls` the pass keeps what it recorded and ends. A batch of several entries now closes at about twice `stm.triggerTokens` (8 bytes per token, at least 32 KB) instead of half of `worker.maxMessageBytes`; only the latter cuts an entry. The reflector and dropper are unchanged.

- **Recall reads events, chunks and tombstones (plan 217 Task 4).** `recall { id }` on an STM record returns its kind, description, time, count and source ids, then every chunk verbatim from the chunk store (read with the executing session's id), or `chunk dropped: <reason>` (`record superseded by <id>`, `record dropped`, `record tombstoned (<reason>)`, or no referrer in this session's store). The raw source entries (`Source evidence:`, the tool value's `sourceEntries`) now come only with `detail: "full"`; the summary no longer carries them. The tool value gains `state` (`active | dropped | reflected | tombstoned`), `tombstone` and `chunks`. An id the session's ledger does not hold answers `unknown_id` (was `not_found`), with the same text whether or not another session has it. New ledger record `memory.session.observations.tombstoned` (`OBSERVATIONS_TOMBSTONED`; `observationIds`, `reason`, `at`; types `ObservationsTombstonedData`, `MemoryTombstone`): tombstoned records leave the active set and the context block and stay findable by id (plan 218's WM writes it). `ObservationalMemoryLedger` gains `dropReasons` and `tombstones`. The context block ends a record with chunks with ` [chunk]` and never renders chunk text; its header says what `[chunk]` means.

- **Habituation and event boundaries (plan 217 Task 3).** An STM event whose `kind` and normalised description match one of the newest `stm.habituation.windowEvents` active records (default 50, tuning) or an event of the same batch, with byte-equal chunks or none, raises that record's `count` and `lastAt` instead of adding a record; `record_event` answers `{ ok: true, habituated, count }`, and different chunk bytes make a new event. The new ledger record `memory.session.observations.repeated` (`OBSERVATIONS_REPEATED`) carries the absolute count. `stm.habituation: false` records every event. The context block and the STM recent index show `×N`. Boundary markers (`memory.session.boundary.recorded`, `BOUNDARY_RECORDED`; reason `outcome`, `task_state` or `idle_gap`) are recorded at no model cost on an outcome event, a task-state content change, and a user turn after `stm.boundaryGapMinutes` (default 10, tuning) of silence; `ObservationalMemoryLedger` gains `boundaries`. New `stm.boundaries` (default `false`): `true` runs an STM pass below `stm.triggerTokens` when the tail holds an idle-gap user turn, at most one extra STM call per boundary. New exports: `OBSERVATIONS_REPEATED`, `BOUNDARY_RECORDED` and the `ObservationsRepeatedData`, `BoundaryRecordedData`, `MemoryBoundary` and `MemoryBoundaryReason` types. The default STM instruction gains one sentence on repeats (about 1,380 bytes, was 1,230).

- **Verbatim chunks in a reference-counted chunk store (plan 217 Task 2).** `record_event` takes `chunks` (at most `stm.maxChunksPerEvent`, default 2, `0` removes the argument): `{ sourceEntryId, text }` excerpts that must be a whitespace-normalised substring of a cited batch entry, or the event is refused with `chunk_not_verbatim` (also `chunk_unknown_entry`, `too_many_chunks`, `empty_chunk`, `invalid_chunks`, and `chunk_budget_exceeded` when a batch's chunks pass 25% of its transcript bytes). A chunk is redacted with the session's secret set and capped at `stm.maxChunkBytes` (default 4,096); the truncation marker names sizes only. The ledger keeps only `chunkRefs`; the text lives in a chunk store (new `stm.chunkStore`: `"memory"`, the default, or `{ sqlite: { path } }`, created mode 0600 with `secure_delete` on), or in a `ChunkStore` a package provides as the `memory.chunks` service. Chunks are reference-counted by referrer (tier, record id, session id): dropping an STM record (rehearsal or `supersedes`) removes its referrer, and at zero referrers the chunk is hard-deleted in the same transaction; a forked or resumed session adds its own referrers when it opens. Each pass makes one store transaction after its ledger appends. New exports: `createSqliteChunkStore`, `SqliteChunkStore`, `MEMORY_CHUNK_STORE_SERVICE` and the `ChunkStore`, `ChunkOp`, `ChunkReferrer`, `ChunkStoreLocation`, `ChunkPrepareFailure`, `PreparedChunk` and `StoredChunk` types. The default STM instruction gains one sentence on chunks (about 1,230 bytes).

- **Short-term memory records events, not facts, and never sees the scope (plan 217 Task 1).** The STM worker's tool `record_observation` is replaced by `record_event` with no alias: it takes `kind` (`request | action | result | change | decision | outcome | error | statement`, required), `description` (was `content`, no alias), `sourceEntryIds` (required), `referencedAt`, `relevance` and `supersedes`, and answers `invalid_kind` / `empty_description` / `invalid_event` when nothing was stored. The default instruction (`DEFAULT_STM_INSTRUCTION`, was `DEFAULT_OBSERVER_INSTRUCTION`; the worker module is `workers/stm.ts`, `runStm` was `runObserver`, all internal) records every meaningful event in order and requires an `outcome` event naming what was asked, what changed, what was achieved or left open, and how it was verified; it no longer asks for "durable source-backed facts". `MemoryObservation` (the STM record) gains `kind`, optional `chunkRefs`, `count` and `lastAt`, and `content` is renamed `description`; ledgers holding records without `kind` or with `content` are skipped by the fold (experimental line, no reader kept). An STM request carries only the batch, the task state, and an index of recent STM records (id, kind, first 120 characters) within the new `stm.contextTokens` (default 4,000, tuning); it replaces the former "Existing active observations" list, which was bounded by a quarter of `rehearsal.targetTokens` and carried full text. The context block renders `kind: description`; WM (the reflector), rehearsal (the dropper), recall and LTM promotion read the new shape.

- **Long-term working memory, the episode view and episode merge removed (plan 216 Task 7, owner decision 2026-11-08).** The working-memory name belongs to the WM component now. Removed with no alias: `kind: "working"` and labeled blocks (`MEMORY_FABRIC_WORKING_KEY`, `FABRIC_BLOCK_LABEL`, `readFabricBlock`, the `fabric-working` tail block), the `block` parameter of `memory.insert`/`memory.replace`/`memory.forget` and `working` in `memory.recall` `kinds`, config `ltm.workingMemoryTemplate` and `ltm.limits.maxWorkingMemoryBytes` (and `"working"` in `ltm.inject.kinds`), `createMemory`'s working API (`getWorking`, `updateWorking`, `deleteWorking`, `renderWorking`, `createWorkingMemoryProcessor`, options `workingStore`, `schema`, `validateWorkingMemory`, `workingMemoryTemplate`, context option `includeWorking`), `createMemoryWorkingStore`/`MemoryWorkingStoreOptions`, `MemoryOkfStores.workingStore`, `ExportMemoryOkfResult.working`, and `MemoryConformanceStores.workingStore`. `remember({ kind: "working" })` fails with `working_memory_retired`. The episode view (`remember({ kind: "episode", id })` over an observational-memory id) and episode merging (`ltm.lifecycle.merge.episodes`, `EPISODE_MERGE_*`, `episodeClusters`, `summarizeEpisodeCluster`, the report field `episodesMerged`) are removed; `episode` stays a reserved kind and writing it fails with `episode_kind_not_available` until plan 219. `createLongTermMemory({ observational })` stays for `reflectionId` promotion and `searchConversation`. With `semantic: false` only file paths remain writable through the tools. The presets' context blocks are unchanged; their tool schemas lost the `block` parameters and the `working` kind (the plan 210 golden was re-pinned and the re-pin recorded).

- **Components, partial-use profiles and fail-closed composition (plan 216 Task 6).** `stm`, `wm`, `rehearsal`, `ltm` and the new `sleep` (a no-op until plan 221, with no fields) each take an object (on) or `false` (off); omitted (`null`), `stm` is on, `wm` follows `stm`, `rehearsal` is on only when `wm` and `ltm` both are (owner decision 2026-11-09), and `ltm` and `sleep` are off. A configured component whose dependency is off fails `createAgent` (`setup_failed`) with a `memory_system_component_missing` message naming both components (`wm` without `stm`; `rehearsal` without `wm` or `ltm`; `sleep` without `ltm`); `resolveMemorySystemComponents` runs the check without an agent and throws `MemorySystemError`. A component that is off loads and registers nothing and its code is not imported: with `stm: false` the package claims no `compaction` slot, with `ltm: false` it registers no `memory.*` tool and no `memory.ltm` service. The package's capabilities are computed from the enabled components through the kernel's new `capabilitiesFor`. **Behaviour change:** a host with the session tiers and no `ltm` no longer runs the dropper (rehearsal is off); the rendered context stays bounded by `rehearsal.targetTokens`. New `memory.system` service (`MEMORY_SYSTEM_SERVICE`): `status()` returns the enabled components; `setScope`, `endEpisode`, `rehearse` and `sleep` reject with `not_available_yet` until plans 218, 219 and 221. `resolveMemorySystemConfig(input, components?)` accepts `false`/`null` sections and its result's `wm` and `rehearsal` gain `enabled`. Profiles (`ltm`, `session`, `stm`, `full`) are documented recipes in the README's `## Profiles` and run in `examples/memory-system.ts`.

The package's capabilities add `credentials` and `host-ui` (long-term memory's). Session state the old package wrote under its own name (the `fabric.*` keys) is not read by the new one. The fabric's history follows below.

### Fixed

- The ledger fold reads the package's own log records off a branch (plan 157 Further Action 1). `state.log` keeps each record as one `package_state` entry whose payload is `data.value`, and `foldObservationalMemoryLedger` (via `recordData`) skipped that wrapper: a consumer holding only the branch — the memory fabric's `observational` source, a host projection, `coverage-helpers` — folded an empty ledger for a session the package had recorded. A `set` state value is still not read as a record.
- `foldObservationalMemoryLedger` no longer throws on a sourceless entry. The reopen-recovery fold maps a branch's entries through `recordData`, which yields a bare `undefined` for an entry with no `data` (any `message` entry); `isSessionEntry` then read `.kind` off it and crashed the context cache. It now skips anything that is not an object, which is what the fold's contract already said ("Anything else is skipped").

### Changed

- Export surface (plan 188.11 Task 5): the root exports the config schema, the ledger record names and folds, `buildObservationalMemoryContextBlocks`, `createMemoryId`, and the shared helpers `memory-fabric` imports. The observer, reflector and dropper workers and their prompts, the settings family, flush, commands, the recall tool, the compactor and every `DEFAULT_*` / `HARD_*` / `OM_*` constant are no longer exported. `root-exports.test.ts` freezes the set.

- **`context.compactAt` replaces `context.compactAfterTokens` (plan 194 Task 7).** The gate is relative now: `{ ratio?: number; maxTokens?: number }`, default `{ ratio: 0.6 }`, resolved as `min(ratio × resolveInputCap(model), maxTokens)`. A model with no declared window uses `maxTokens`; without it the gate fails with a field-naming error. The legacy settings surface (`ObservationalMemoryContextSettings`, `defaultObservationalMemorySettings`, `resolveObservationalMemorySettings`) carries the same shape, and `om:status` reports `thresholds.compactAt`. `DEFAULT_COMPACT_AFTER_TOKENS` is removed; `DEFAULT_COMPACT_AT_RATIO`, `resolveCompactAtThreshold`, `MemoryObservationalCompactAt` and `ResolvedCompactAt` are exported.

- `context.trigger` replaces the token gate (plan 157 Task 5): set it to a JSON-safe `CompactionTrigger` and the package's `compaction.when` handler composes `resolveShouldCompact` with it instead of comparing `context.compactAfterTokens`. While on, the handler also votes `{ compact: false }` below its gate (plan 194 Task 2), so the host's `thresholdEntries` fallback cannot override OM; with the toggle off it abstains. `om:model` also accepts `reset: true` (clear the stored worker refs so the session model is used again) and `om:status` reports the effective `observer`/`reflector` refs. The model-ref config keys now accept a model object as well as a `"provider/model"` string (the outer schema node stays open so the `anyOf` branch validates the keys).

- `recall.gather` (plan 210 Task 3.1, opt-in, default off): adds `gather` to the `memory.recall` tool; a gather call returns the whole matching history (up to 32 hits) oldest first with a 3,000-token snippet budget. `CreateMemoryFabricOptions.gather` and `MemoryFabricToolDeps.gather`; the resolved config's `recall` gains `gather`. With the field unset the tool schema is unchanged.

- `recall.expansion` (plan 210 Task 3.1, opt-in, default off): the lexical query is expanded with the informal and formal forms of its words from a small fixed English table (`lexical-expansion.ts`, `expandLexicalQuery`); the relevance floor is scaled by the share of the caller's own terms. `CreateMemoryFabricOptions.queryExpansion`; the resolved config's `recall` gains `expansion`.

- `inject.cardExcerpt` (plan 210 Task 3.1, opt-in, default `"head"`): `"query"` renders a pointer card as the same 120-character width centred on the query terms across both halves of the exchange. `fitInjection` takes an optional eighth argument `cardExcerpt`.

- `recall.supersessionHint` (plan 210 Task 3.1, opt-in, default `"all"`): `"keyed-only"` limits the read-time "superseded by" marker to members joined by a key or a `supersedes` edge. `groupRecallHits` takes an optional `{ supersessionHint }`; `CreateMemoryFabricOptions` and `MemoryFabricToolDeps` gain `supersessionHint`; the resolved config gains `recall`.

- `directory.stopWords` (plan 210 Task 3.1, opt-in, default off): the memory directory's topic list can drop topics made only of stop words (`i`, `it`, `we`). Unset, the list is unchanged. Added to `ResolvedFabricDirectoryOptions` as `stopWords: boolean`.

- Recall grouping no longer buries the best match (plan 208 Task 5, 2026-11-04): read-time grouping (`groupRecallHits`) joins an exchange to a group only when it shares subject terms with that group's best-ranked member, and no longer chains loosely similar exchanges together; a subject term carried by at least 80% of five or more exchange hits in one result (a speaker's name, say) does not count. Before, every turn of a two-person conversation shared both names, the whole result became one newest-first group, and the only note matching every query term could land last, past the recall page the model is shown. Same-key and `supersedes` grouping and the `supersededBy` hint are unchanged.

- Unbound notes without keywords reach the wiki (plan 208 Task 5, 2026-11-04): the `memory.fabric` port's `OntologyNoteView.keywords` falls back on the archive path's deterministic `exchangeKeywords(text)` for an evidence note stored without keywords (a `remember` call or an import that passes none). Before, such notes never shared a keyword, so the wiki's unbound-cluster trigger could not see them and the ontology tier did nothing on them. View only: the stored note, recall's keyword weight and the directory are unchanged; concepts and `file` notes keep what they stored. Without the wiki package nothing changes.

- Source seam for the wiki (plan 207 Task 8): the `memory.fabric` port gains `sourceRoot()` (the fabric's `tools.root`, or `undefined`) and `indexSource({ path, text, contentHash, keywords })`, which runs the trust scan and then the ordinary write path for a `kind: "file"` note in the `project` scope: deterministic subject binding, dirty marking, no model call. A text the scan flags returns `{ indexed: false, refused }` and writes nothing; a fabric with no `tools.root` throws. `OntologyNoteView` carries `path` for `file` notes, and `OntologySourceInput` and `OntologySourceResult` are exported. The startup reconcile skips an ingested source's immutable original (`sources/<id>/source.<ext>`), which may be binary and would duplicate its `extract.md`. Additive; without the wiki package nothing changes.

- Human curation of concepts and the team ontology (plan 207 Task 7): a person's edit to a concept file is reviewed before it is indexed, in the private store and the checked-in team store alike, with no model call. A body that breaks the item grammar is rejected: the last valid version stays indexed, the file is left as written, and `log.md` gets one `invalid-concept` line (the writer is `human`). A claim whose text or citations changed, and a new claim, is marked `[c1 human]` in the file (a new part of the body grammar: `ConceptItem.human`); a marked or uncited claim is read-only to every writer but a person, and the port refuses `update_claim`, `retire_claim` and `merge_claims` on it with `claim_human`. `sources` and `title` are re-derived from the body, the stale mark of a changed claim is cleared, the concept gets the dirty reason `edited`, and `generated` becomes `human`. The trust scan runs on the title, aliases and body: a hit quarantines the concept as a `candidate` with `flags`, and a clean edit lifts it. `memory:reindex` invalidates the concept index. With `team` on, the team concepts are a read-only scope of the `memory.fabric` port (`scopes()` lists `team`; `applyConceptEdits` and `bind` on it fail with `MemoryScopeError`). The ontology `OntologyScope` may name its own `store`. Additive; with no concept file edited nothing changes.

- Curator port surface (plan 207 Task 6): the `memory.fabric` port gains what the wiki's concept pass needs. `pending` takes `subject`, `unbound` and `coRead` filters, evaluated in the same metadata scan; a note view carries `keywords`, `links`, `coRead`, `generatedBy` and, for a concept, `stale`; `settle(scope, subject)` clears a subject's `evidence` dirty reason when the curator had nothing to add; `screen(text)` names the trust class the fabric would refuse, so one offending edit can be dropped. All additive; nothing changes without the wiki package.

- Concepts first, then drill down (plan 207 Task 4): `memory.recall` is the one retrieval surface for the ontology tier. `concept` joins the default recall kinds and `kinds: ["all"]`, and a concept hit gets the tuning-tier kind prior `ontology.conceptPrior` (default 0.1, in [0, 0.5]) after fusion and the scope prior, so it outranks its own evidence but not a better-matching note. The recall tool renders a concept as a header, its current claims with the ids they cite (`ontology.maxClaimsRendered`, default 8, in [1, 32], chosen by term overlap) and a `drill down: memory.read { ids: [...] }` line; a stale claim, a claim with an unreadable citation and everything under a flagged concept are not rendered, and an uncovered pattern still returns as a plain note in the same call. `memory.read { id }` returns a whole concept with claim ids and `(stale)` / `(uncited, human)` labels; reading a note lets the model cite it. Passive delivery is a pointer only: at most one `- [id] concept <subject> — memory.read <id>` line per turn, for the top fused hit when a name is in the turn or a touched path is in its `appliesTo`; a path cue shows the same pointer, never claims, and a concept never enters the pinned core. `memory:share` accepts a verified concept (current claims only; the cited private notes are not copied; one per subject; a private concept shadows a team concept by subject). An answering turn that cites two or more received notes records a `coRead` event (`{ s, t, with }`, ids and indexes only, last 16 per note) in the existing lifecycle write, and a recorded use refreshes the concept's index row so the directory order follows use. `memory.recall` with `kinds: ["concept"]` is refused (`concept_requires_ontology`) only when `semantic` is off. New config: `ontology.conceptPrior`, `ontology.maxClaimsRendered`. New note field: `coRead`. No model call, no kernel change; with no concept notes every result is byte-identical.

- Ontology index and schema-assisted subject binding (plan 207 Task 3): a new T1 note is bound to the one subject it names when it is written. The scope's concept index feeds a token map built with the lexical index's own normalizer; exactly one subject with at least `ontology.bindThreshold` matched name tokens (default 2, tuning, in [1, 8]) or one whole multi-token alias binds the note, otherwise it stays unbound. No model call, never across scopes, and a note whose index cannot load is stored unbound. Binding marks the concept `dirty: ["evidence"]`. The consolidation extractor's per-call prompt lists the scope's subjects (≤ 64 per scope) and `record_notes` gains an optional free-string `subject` (a shown slug or `new`; anything else is dropped); its cached system text and tool bytes are identical with and without an ontology. A concept gets a directory line, `project concepts: 12; subjects: a, b, c (+9)`, inside the existing budget and pinned for the session epoch. `CreateMemoryFabricOptions.subjects` takes `createFabricOntology(...).subjects`; the package wires it. Fixes a Task 2 gap: a reconsolidating rewrite no longer drops a note's `subject`. With no concepts nothing changes.

- Ontology tier, store side (plan 207 Task 2): a new opt-in `concept` note kind (one per subject: itemized claims, each citing T1 note ids with OKF footnotes, closed relation set `part-of`/`instance-of`/`uses`/`related`) and an additive `subject` field on every kind. A use is a citation of a shown id, logged once per session per note as `{ s, at }` (scope-session ordinal and wall time) and counted in `useSessions`; a candidate verifies at `lifecycle.verifyAfterSessions` (default 2) distinct sessions with no harmful evidence, or by an explicit confirmation. Outcome tags record `helpful`; a user correction citing a note records `harmful`, sets `reconsolidate: true`, and returns a verified note to `candidate`. `retrievals` counts returns and never affects status. `MemoryNote` exposes `useSessions`, `retrievals`, `helpful`, `harmful`, and the capped `uses` log; `MemoryFabric.recordUse` is now `recordUses(sessionKey, ids, { clock, verifyAfterSessions })`. Retired: `promote.verifyAfterUses`, `lastUseKey`, the scoped ledger's per-note lifecycle rows, `touchScopedLedger`, `runScopedPromotionPass`, and `policy.promotionPass()`. The ledger keeps pending approvals and write statistics only, reads an older file with its lifecycle rows ignored (reported once), `scopedMemoryHealth(memory, ledgerFile)` reads the unified lifecycle, and the scoped reader records no use on retrieval.

### Fixed

- Lifecycle defect fixes (plan 188.1 Task 11 — D4, D5, D13):
  - D4: Superseded reflections retire their promoted notes with supersedes semantics (`validTo` set, correction lineage preserved, and logged as `superseded-by-om`). Replacement reflections created in the same pass are linked via `supersedes`. Verified notes edited after promotion (carrying correction lineage) are not retired; they are preserved with `reconsolidate: true` and surfaced in `memory:status`.
  - D5: Verification by use, not retrieval: `memory.recall` drops unconditional `touch` and `recordUse`. Recalled and injected note IDs share a unified `FabricCitationTracker` (`createFabricCitationTracker`). Usage increments only when the assistant cites a note (`[id]`) in turn completions, keyed by distinct session ID. The recall tool output prompts: `"Cite [id] for notes you use."`.
  - D13: Archive separate from validity: `archiveStale` sets `status: "archived"` and `archivedAt`, never setting `validTo`. Active recall, injection, and directory walks exclude archived notes via a unified `isActiveNote` predicate in `lifecycle.ts`. Historical time-scoped recall (`asOf` prior to `archivedAt`) sees archived, non-superseded notes as valid.

### Added

- Session consolidation, step 5 — triggers, cursor, command and status (plan 188.3 Task 5): the pass is wired to three triggers — `turn.completed` after `promote.minTurnsBetween` turns when OM recorded a new reflection, supersession or task-state decision after the cursor; `memory:consolidate`; and `session.opened` with `restored: true` (one catch-up) — with no timers and one pass per session at a time (a trigger during a running pass is dropped, not queued). The cursor advances only after every write succeeds, so a failed pass fails only its background task and retries on the next trigger. `fabric.consolidate(session, { signal, cursor })` is the host API (call it, or the command, before `session.close()`), `memory:status` now reports the last pass's counts and rejections by reason (`score`, `ephemeral`, `derivable`, `trust`, `secret`), and `promote` is reshaped to `false | { model, minScore, weights, maxCandidates, minTurnsBetween, derivableFrom, verifyAfterUses, archiveAfterDays }`, default `false` (no model call). Superseded reflections are handled by the pass, and a `reconsolidate` note is shown to the extractor as an existing note, rewritten in place by key/kind/scope, or retired when the extractor returns nothing for it.

- Session consolidation, step 4 — the write path (plan 188.3 Task 4): accepted notes go through the same `remember` an agent write uses, each stored with `status: candidate`, `generated: { by: "promotion", at, session }`, `sourceEntryIds`, and a `promotion: { score, signals, pass }` stamp. A contradiction of a wider-scope note is written as an exception in the narrower scope with the same `key` and `overrides` naming the wider note, so plan 188.2's key shadowing hides the wider note in that project only; the wider note records the project id in `contradictedIn` (deduplicated, ids only). Same-scope contradictions keep both notes linked `contradicts` and route to the decider's `SUPERSEDE` when configured. Reconsolidating notes are rewritten in place with the same id and correction lineage, or retired (`validTo`) when the extractor returns nothing for their key; a verified note is never demoted, and a flagged or archived one is never rewritten. New `overrides`, `contradictedIn`, and `promotion` note fields are parsed fail-closed. Per-reflection promotion is removed: `runFabricPromotion`, `promote.observational`, and the per-turn reflection trigger are gone, and `promote` now only configures the candidate lifecycle.

- Session consolidation, step 3 — scoring and the promotion gate (plan 188.3 Task 3): `scorePromotion(note, context)` returns `{ score, signals, accepted, reason }` from a transparent linear score — `explicit + correction + outcome·0.5 + recurrence·0.5 + generality·0.5 − ephemerality − derivability − duplicate·0.5` — with weights as exported data (`DEFAULT_PROMOTION_WEIGHTS`) and a default `minScore` of 0.5, provisional until plan 188.6 calibrates them. `explicit` and `correction` are cross-checked against the evidence's gathered candidate sources; `recurrence` is `log2(1 + distinct sessions)` normalised to 1 at four sessions; `ephemerality` rises to 1 for line references, temp paths, commit hashes, branch names and outlived dates; `derivability` covers the extractor flag and ≥ 0.9 lexical coverage by a `derivableFrom` file; `duplicate` is the highest Dice with an active note of the same kind in the target scope. Rejections carry one reason (`ephemeral`, `derivable`, `score`); an explicit user statement is never rejected for score. `loadDerivableSources(root, files)` reads those files once per pass through the fabric file jail (inside the root, 64 KiB cap) and reports `../`, absolute and symlink escapes as skipped notes instead of trusting them. No model call.

- Session consolidation, step 2 — the extractor (plan 188.3 Task 2): `extractConsolidationNotes({ client, candidates, segments, recallExisting, limits, redactor, secrets })` makes exactly one model call per pass through the shared worker loop, with one schema-declared tool, `record_notes`. The schema in `consolidation/prompts.ts` is the single source for the tool definition and for parsing, so an answer can only cite the candidates (`c1`, `c2`, ...) and existing-note ids it was shown. It returns atomic, typed notes — `fact`, `procedure`, `preference`, `episode` — with a proposed scope, keys and aliases, evidence ids, generality and ephemerality, and contradictions; `agent` scope is downgraded to `project`, and an episode is one per task segment at 280 characters or fewer. It fails closed (`ConsolidationExtractionError`, nothing written, cursor kept, one warning, retried on the next trigger) on a malformed answer, an unknown kind or scope, an unshown evidence or `contradicts` id, too many notes or an oversize item; an aborted call aborts the pass. The trust scan and the secret redactor drop individual notes and count them as `rejected.trust`/`rejected.secret`. Input is bounded by `workerLimits` before it is sent, and the default package load resolves no model client.

- Session consolidation, step 1 — candidate gathering (plan 188.3 Task 1): `gatherConsolidationCandidates(entries, { cursor, maxCandidates, maxTextChars, patterns, redact })` is a pure, bounded function over `session.entries()` that makes no model or store call. It gathers reflections no later record superseded, `om.task_state.recorded` decisions, `high`/`critical` observations, explicit user statements (matched sentence only), corrections (carrying the corrected assistant entry and the note ids cited in that turn), and tags candidates whose evidence shares a run with a successful test/commit tool result or an approval grant. Candidates are priority-ordered (explicit, correction, decision, observation, reflection), capped by `maxCandidates` (default 48) and per-candidate text, and idempotent for the same cursor. `CONSOLIDATION_PATTERNS` exports the default English pattern sets. Assistant text is never an explicit candidate and tool output is never candidate text (MINJA).

- Fabric OKF export and import for every store: `exportMemoryOkf(memory, { dir, stores })` writes the thread's notes, working memory, tombstones and holds, `index.md`, and `log.md` in the markdown layout (no embeddings), and `importMemoryOkf(memory, { dir, stores, mode })` reads a bundle into any store (SQLite, Postgres, in-memory, markdown). Imports stamp `generated.by: import`, scan every note and quarantine hits as candidates, re-embed only when an embedder is passed, and never clear or overwrite a target's legal hold. New `memory:export { dir }` and `memory:import { dir, mode }` commands resolve `dir` inside `tools.root` (plan 188.1 Task 7).

- Provenance and poisoning defenses (plan 188.1 Task 6): every durable write stamps `generated: { by, at }` (`agent` with the session id, `promotion` with the reflection and evidence ids, `human` for an external edit found by reconcile, `import`, or `host`). The markdown store's `log.md` records the actor on each line. Reconcile runs `scanScopedMemoryContent` once per externally changed file: a hit sets `status: candidate` with `flags: [<class>]`, rewrites the note, and logs `flagged`. Flagged notes are never injected passively and `memory.recall` marks them `[flagged: <class>]`; `memory.replace` or a clean human edit clears the flag. Injected fabric blocks carry the `untrusted`/`inert`/`injectionCapable` envelope. The scan is heuristic — review `log.md` and `git diff` (MINJA).

- The store defaults to markdown when `tools.root` is set: `store: "markdown" | { markdown: { dir } }` (default `notes`) writes canonical OKF note files with a derived `.index.sqlite` under the root, browsable with `memory.view`/`memory.read` and editable in place. `memory.replace { id }` rewrites the note file (a `corrected` invalidation no longer archives it), the file reconcile and directory walk skip `notes/**` as user files (the directory names `notes/index.md`), and the new `memory:reindex` command rebuilds the derived index and reports `indexed`/`removed`/`malformed` (`{ full: true }` re-reads every file). `{ sqlite }` and `{ postgres }` stay available but need `memory:export` to be inspectable.

- The memory family's cross-package integration suites (plan 158 Task 6): with the `@arnilo/prism-memory` workspace deleted, its remaining `__tests__` tree moved here — lineage, deletion propagation, grant-change source re-pointing, host wiring, eval revocation, RAG ACL, and the three Postgres integration suites. `@arnilo/prism-memory-rag` and `@arnilo/prism-memory-wiki` are development-only dependencies, `test:postgres` runs the Postgres legs, and `no_workspace_imports_prism_memory_family` guards that only frozen records name the retired family.
- `@arnilo/prism-memory-fabric` (plan 158 Task 4): the 0.12 memory fabric (typed notes,
  consolidation, the opt-in linker/evolution workers, working memory, the `createMemory` engine,
  the memory conformance harness) and the scoped policy layer moved out of
  `@arnilo/prism-memory/{fabric,scoped}` into their own package, plus the `memory.view`,
  `memory.read`, `memory.insert`, `memory.recall`, and `memory.forget` tools, a `context.build`
  block, and per-session enablement.
- Semantic memory consumes the `embeddings` service another package provides
  (`@arnilo/prism-memory-rag`); without it the package registers working memory only and notes why.
