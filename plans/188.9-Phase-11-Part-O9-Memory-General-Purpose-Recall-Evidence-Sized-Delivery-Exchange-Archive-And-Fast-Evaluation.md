# Phase 11 Part O9 — General-purpose memory recall: evidence-sized delivery, exchange archive, general extractor and fast evaluation

## Objectives

- Make the memory fabric a **general-purpose** memory for both coding and conversational agents (owner decision 2026-10-22). Use-case-specific variants may come later; this plan ships one general design.
- Fix the measurement error that sent 188.8's remediation the wrong way. `answer_gap` mostly counts questions that got only part of their evidence, not synthesis failures.
- Deliver as much evidence as a question needs. Passive injection fills an evidence-sized budget with whole notes instead of fitting about one round into 600 tokens. The candidate floor and top-k are chosen by a pre-registered offline rule.
- Fix the agentic tool defects that make the agent loop:
  - no read-by-id;
  - a budget counted on full notes but shown as 400-character snippets;
  - a snippet window centred on the first match;
  - default kinds that miss the history.
- Give the product a real durable write path for conversation detail:
  - an opt-in **exchange archive** (verbatim user turn plus reply, dated, source-backed, chunked when oversized);
  - a **domain-neutral consolidation extractor** that writes dated, keyed facts linked to their evidence exchanges.
- Make the benchmark measure only what the product can produce: haystacks are ingested through the product write path, not upserted into the vector store.
- Make the experimentation cycle fast:
  - per-call timing evidence;
  - configurable concurrency;
  - answer and judge phases split, with a judge cache;
  - parallel arms;
  - reuse of unchanged reference arms;
  - a paid screen profile;
  - a cached write side.
- Run a paid development screen, then a paid held-out acceptance, under an owner-approved cap. Record the F13 verdict and any evidence-gated default change.

## Expected Outcome

- `retrieval-diagnostics.mjs` reports a `partial_evidence` stage. The committed 188.8 stage counts are re-bucketed in a dated correction note: 17 of the 26 post-fix `answer_gap` rows become `partial_evidence`.
- The diagnostic has a committed ceiling mode (budget × top-k × floor grid over the development partition) that reproduces the investigation's coverage tables.
- Passive injection (`inject` on) shows whole notes, ranked, up to the budget, in chronological order.
  - Defaults for `budgetTokens`, `topK` and `minSimilarity` change only for agents that opt in, and only by the rule fixed in Task 5.
  - `inject` stays off by default unless 188.6's enablement rule is met.
- `memory.read` accepts a note id (or up to 8 ids) and returns the full note.
  - `memory.recall` budgets by rendered tokens, centres snippets on the densest match, and searches every stored kind except `working` by default.
  - 188.8's discovery hint is retired.
- `fabric({ exchanges: {} })` archives every completed exchange as an `exchange` note:
  - one local write per turn, no model call;
  - back-filled by `memory:archive`;
  - split into linked parts when larger than the core entry limit.
- The consolidation extractor is domain-neutral:
  - It reads exchanges as candidates when the archive is on.
  - It writes dated facts with keys and supersession, linked to their exchanges.
  - Coding behaviour is unchanged on the existing consolidation and lifecycle suites.
- Benchmark arms ingest each haystack session through a real session plus `memory:archive` (and `memory:consolidate` for the extraction arm). The write side is cached by content hash and reused by every read-side arm.
- A paid campaign on held-out v2 reports:
  - baseline (188.8 post-fix), delivery, delivery + extraction, agentic, and a reused full-context reference;
  - per-call timing;
  - wall time under one third of 188.8's for the read side;
  - an explicit F13 verdict.

This plan implements roadmap Phase 11 Part O's memory-quality requirement as the next 188.x sub-plan. It follows 188.8's completed campaign and its post-acceptance investigation (below), and absorbs 188.8's Further Actions 1, 3, 4 and 5. **No kernel review task:**

- The plan changes no kernel contract and creates or moves no package.
- Every new behaviour uses existing seams: the fabric package's `turn.completed`/`session.closed` hooks, `PackageAPI` commands, session entries, `context.build`, and the existing link expansion in `recall.ts`.
- Task 1 is a read-only assumption check of those seams, in the style of 188.2's series check. It stops the plan if any seam is missing.

Public surface changes are package-level only, in `@arnilo/prism-memory-fabric` and `@arnilo/prism-memory-core/fabric`:

- a new `exchange` note kind;
- an `exchanges` config field;
- `memory.read` and `memory.recall` parameter changes;
- an `exchange` consolidation source.

Each lands with its compat-baseline regeneration in the same task. No version bump, publish or `/docs` page.

Out of scope, recorded for Further Actions at plan end:

- use-case-specific memory profiles;
- an OM-observations-in-context arm (it costs another full write pass over every haystack, and the extraction arm answers the product question);
- embeddings/hybrid retrieval changes (this plan stays lexical-first).

**M4. Lexical ranking over raw rounds is near its ceiling.**

- Multi-session (3.05 needed rounds on average) has all evidence in uncapped BM25's top 20 for only 10/20.
- Only a different representation (atomic dated facts that act as keys for their source exchanges) can raise multi-session coverage within a bounded budget.

**M5. The benchmark measures a configuration the product cannot produce.**

- `ingestHaystackRounds` (`replay.mjs:236–280`) upserts raw rounds as `kind: "episode"` rows straight into the vector store.
- In the product, `episode` is a *view* over an OM observation, never a stored row (`packages/memory/fabric/src/types.ts:23–27`, `create.ts:258–282`).
- No product path stores past conversation exchanges. Cross-session conversational detail survives only if OM is on and consolidation promotes it.
- The extractor prompt is coding-only: "You consolidate a coding agent's session…", and "Do not record what the repository already records" (`consolidation/prompts.ts:32–41`).
- Candidates come only from OM signals and explicit/correction patterns (`consolidation/gather.ts:25,94–195`).
