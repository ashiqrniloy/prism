# Phase 11 Part O19.1 — Memory benchmarks: external outcome suites replace BEAM and LongMemEval

## Objectives

- Remove `beam-1m` and `longmemeval-m` from every memory-model gate (owner decision, 2026-11-12). They measure question answering over imported chat logs, not the work Prism's memory does: keeping a coding agent's progress across compaction within a session, and carrying results across sessions. At about 1M tokens a question, they also cannot reach a sample size that decides anything (gate M-1: 2 questions per cell; gate M-2: 4).
- Replace them with external, outcome-scored benchmarks that we did not design, so the test is not shaped by the product it judges:
  - **Compact-Bench** for the session tiers (STM, WM, compaction);
  - **MemoryArena** for declarative long-term memory across sessions;
  - **STATE-Bench's Agent Learning Track** for cross-task (procedural) learning and Sleep.
- Re-scope the criteria rows that used the two suites, through one recorded amendment, before any later gate runs.

**Survey (2026-11-12).** Candidates were read at their primary sources:

| Benchmark | Verdict | Why |
|---|---|---|
| Compact-Bench (arXiv 2610.31710; [code](https://github.com/cai-jianfeng/compact-bench) Apache-2.0; [data](https://huggingface.co/datasets/caijanfeng/compact-bench) Apache-2.0) | **adopt (session tiers)** | Scores what compaction costs a coding agent. In task preservation, a frozen SWE-bench repair continues from the full history (PRE) or from the compacted state only (POST), judged by the repo's FAIL_TO_PASS tests. It also counts `redo_reads`, the same signal as our re-derivations. Recurring-detail retention: 146 sessions, 9,330 annotated details, scored by literal string match. It compares five production compaction prompts (Claude Code, Codex, opencode, Gemini CLI, Kimi Code) and a regex reference (`anchor_index`, 79% retention against at most 16% for LLM summaries), so Prism is measured against competitors, not a baseline we chose. The method under test is anything that maps a history to a summary (`harness/e1_runner.py` `compress`, `harness/e2_score.py` `compress_one`). |
| MemoryArena (arXiv 2602.16313, ICML 2026; [data](https://huggingface.co/datasets/ZexueHe/memoryarena) CC-BY-4.0; [code](https://github.com/ZexueHe/MemoryArena), licence not stated) | **adopt (LTM), after the licence check** | 766 tasks of about 6.9 interdependent subtasks. Each subtask is its own session, and later ones need earlier results. It reports success rate and process score. Long context, Letta, Mem0 and RAG all score 0.12–0.23, so there is headroom. Five subsets: bundled shopping, progressive search, group travel, formal reasoning math and physics. |
| STATE-Bench ([Microsoft](https://github.com/microsoft/state-bench), MIT) | **adopt (procedural, Sleep)** | 450 tasks across travel, support and shopping. Success is the sandbox database's final state; pass@1 and pass^5. Its Agent Learning Track adds train trajectories and a retrieval hook for reusable learnings. That is cross-task learning, not a multi-session declarative memory test, so it serves plans 220 and 221. |
| LoCoBench-Agent (Salesforce, Apache-2.0) | **reject** | Its metrics are heuristics that reward the wrong behaviour (`locobench/evaluation/bias_free_evaluator.py`). `multi_session_memory_retention` counts assistant messages containing words such as "previously" plus vocabulary overlap, floored at 0.3. Task completion is the session's self-reported phase rate. Functional correctness regex-matches names in modified files. No tests run. |
| CompactionBench (Microsoft Research) | **watch** | Repeated compaction in persistent coding sessions, with cost and prefix-cache reuse. No code or data found on 2026-11-12. |
| DolphinBench (Mem0), Letta Context-Bench | **not adopted** | Vendor-authored by memory-product companies. DolphinBench's design (solvability-certified action tests, cost and latency) is the bar the adopted suites are held to. |
| MEMTRACK, Mem2ActBench, MemoryCode | **not adopted now** | MEMTRACK: 47 trajectories. Mem2ActBench: tool-argument grounding only. MemoryCode: instruction retention, already drawn (`robustness-memorycode.json`), kept as a reference. |

- [ ] Task 2: Compact-Bench adapter — Prism as the method under test
  - Acceptance Criteria:
    - Functional: `scripts/memory-bench/external/compact-bench/` pins the upstream repository at a commit and the dataset at a revision (`--revision`), with its `SHA256SUMS`. A fetch whose checksums differ is refused.
    - Functional: **Prism as summarizer.** For each history H:
      1. Replay H through an agent session with the arm's memory configuration, using plan 217's session-replay machinery.
      2. Compact once at the end of H.
      3. S is what Prism puts in front of the model after that compaction: the rendered memory block plus the messages the arm keeps, serialized with the benchmark's transcript format.
      The adapter serves S through the benchmark's own `compress` entry points, so the PRE arm, the continuation agent, the tests and the scoring are upstream's, unchanged.
    - Functional: the arms are `memory-off` (the kernel's default compactor), `OM-before` (the pinned worktree), `STM-only` and `WM`. The five production prompts and `anchor_index` are the external references.
    - Functional: **Draws.** Retention sessions are split label-blind into dev / heldout-a / heldout-b (the `drawLongSessionPartitions` rule, seed `prism-218.1-compact-bench`), stratified by `client`. The task-preservation track is reserved whole for gate A; a development gate that reads it is refused.
    - Functional: the continuation agent and summarizer routes are named in each gate record. Kimi K3 is the upstream default continuation agent, and its thinking is disabled upstream.
    - Performance: the retention track needs no continuation agent and no repository build. Its cost is the arm's own memory calls over 146 histories.
    - Code Quality: the adapter is a thin bridge. Upstream Python runs from a pinned checkout in its own directory (untrusted code, run with `python -I`); nothing upstream is vendored.
    - Security: the upstream code and data are untrusted input. The adapter passes paths as arguments and never runs upstream code from inside the Prism tree. Credentials reach upstream only through its documented environment variables, never argv.
