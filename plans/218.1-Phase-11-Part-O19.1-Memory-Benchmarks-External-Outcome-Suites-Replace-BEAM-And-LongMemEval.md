# Phase 11 Part O19.1 — Memory benchmarks: a lean external screen replaces BEAM and LongMemEval

> **Amended 2026-11-13 (owner, memory evaluation; design §14):** Task 3's Step 1 probe, running on 2026-11-13, finishes unchanged. Step 2 (the paid screen) waits for [plan 218.2](218.2-Phase-11-Part-O19.2-Memory-System-Session-Tier-Hardening-For-Small-Workers-Durable-Signals-Recall-Query-Verdict-Format-And-Baseline-Arms.md), which changes the STM and WM workers the screen would measure. After plan 218.2 Task 9 the probe is re-run on the new product hash, and that reading selects the branch. Both branches gain a `mask-tail` reference.

## Objectives

- Remove `beam-1m` and `longmemeval-m` from every memory-model gate (owner decision, 2026-11-12). They measure question answering over imported chat logs, not the work Prism's memory does: keeping a coding agent's progress across compaction. At about 1M tokens a question, they also cannot reach a sample size that decides anything (gate M-1: 2 questions per cell; gate M-2: 4).
- Answer the question that matters now, cheaply and quickly, on an external benchmark we did not design: **is STM + WM worth shipping as the session memory, over no memory, the pre-redesign observer, STM alone, and a production agent's own compaction prompt?**
- Defer everything a cheap screen cannot settle: the second model, held-out partitions, long-term memory suites and the full gate A. These run only if and when the owner chooses to spend on them.

## Expected Outcome

- `memory-model-criteria.json` amendment 6 removes the two suites from every row. Rows whose new suite is deferred read `missing` until it is adopted, never `pass`.
- `scripts/memory-bench/external/compact-bench/` holds a pinned adapter: Prism as the method under test, plus a thin local pass-through to OpenCode Go. It adds the required `x-opencode-session` header, records usage and sets the agent's thinking level; MiniMax M3.1 Flash is the continuation agent on its native Messages route.
- One **lean screen** (Task 3), with its decision rule written into the gate record before the run (amended 2026-11-13, owner: a WM engagement probe of about $0.25 gates the screen first, and the outcome screen becomes opt-in; see Task 3):
  - a retention screen on 30 sessions;
  - an outcome screen on the 22 validated repair tasks;
  - one model family, OpenCode Go only, **about $6–10 and half a day of runs**.
- Plan 218 Task 6 (gate M-2) reads the screen in place of M5 and runs no QA suite job.

This plan implements the owner's benchmark decisions of 2026-11-12, made after plan 218 Task 6's first sitting. It runs before Task 6 resumes. **No review task:** it changes no product contract, only the bench harness, the criteria file and the evidence. No version bump and no publish. **Claude Code is not used** for any benchmark call (owner, 2026-11-12: its system prompt would be part of what is measured). `locomo` and `memoryagentbench-cr` (also QA) stay where plans 219.1 and 222 use them until the owner decides.
