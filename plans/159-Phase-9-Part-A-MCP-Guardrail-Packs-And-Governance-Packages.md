# Phase 9 Part A — MCP, guardrail packs, and governance packages

## Objectives

- Run the Phase 9 review for both parts. It inventories the 0.12 MCP client, governance, identity, guardrail-pack, model-router, observability, and delegation code. It classifies every Scope bullet and records the decisions both parts build on.
- Add only the kernel seams the review confirms. The survey for this plan found two candidates:
  - config provenance by manifest scope, so a package can tell project-declared config from user or host config
  - a package-visible handle on the agent's loaded package instances, so `delegate` (Part B) can build a child agent from a chosen subset
- Split the 0.12 `@arnilo/prism-mcp` workspace. Its server half moves unchanged to the host library `@arnilo/prism-mcp-server` (Phase 10 reshapes it). Its client half becomes the native package `@arnilo/prism-mcp`:
  - stdio, URL, or raw transports
  - `allow` fail-closed
  - a connect failure is a status, not a failed `createAgent`
  - project server trust via `host.ui`
  - header values as credential refs
  - status, reconnect, and close as commands and events
- Make the built-in guardrail packs the native package `@arnilo/prism-guardrail-packs` over `tool.call` and `tool.result`, and retire the kernel's `SessionOptions.guardrailPacks` path.
- Make the policy engine, OPA, audit sink, identity verification, and principal enforcement the native package `@arnilo/prism-governance`.
- Move the governance and identity modules out of the kernel: `src/identity.ts` (except `Principal`), `src/secure-agent.ts`, `src/host-composition.ts`, `src/field-policy.ts`, `src/field-evidence.ts`, and `src/evidence-grounding.ts`, as the review assigns them.
- Prove both Phase 9 Done criteria with examples under the execution gate.

## Expected Outcome

- `packages: [mcp({ servers: [...] })]` connects each allowed server during `setup` with a bounded timeout, and registers its tools with `effects`.
  - A server outside `allow` is never connected and is reported `disabled`.
  - A connect failure is a `failed` status, a `mcp.status` package event, and a status note. `createAgent` still succeeds.
  - A project-declared server spawns only after `host.ui` `confirm` answers yes. `dismissed` or `unavailable` means it never spawns.
  - Header values are `env:`/`keyring:` refs, resolved through the credentials slot. They never appear in events, `inspect()`, errors, or status text.
  - `mcp:status`, `mcp:reconnect`, and `mcp:close` are package commands.
- `packages: [guardrailPacks({ packs: ["destructive-commands", ...] })]` enforces the built-in packs through `tool.call` and `tool.result`. Its pack state survives a resume through package session state. `SessionOptions.guardrailPacks` no longer exists.
- `packages: [governance({ default: "deny", rules: [...] })]` decides every `tool.call` through the policy engine (inline rules or OPA), records each decision to the audit sink, and fails closed when OPA or the verifier is unreachable. With `identity` configured, it verifies the session's principal before a run, and enforces it on every tool call.
- `examples/mcp-trust.ts` shows that an untrusted project stdio server never spawns and a header ref is never echoed. `examples/governance-deny.ts` shows a deny-by-default policy blocking a tool. Both run under the execution gate.
- The kernel root no longer exports `AgentIdentity`, `IdentityVerifier`, the identity helpers, `createSecureAgent`, the guardrail-pack compile surface, or whichever field-policy and evidence modules the review moves. `Principal` stays in the kernel. Every importer is migrated, and the baselines are regenerated.

This plan implements roadmap **Phase 9 — Integrations, policy, and governance packages**, Part A. **Part B is plan 160**, which depends on this plan; it covers `model-router`, `observability`, `delegate`, and the Phase 9 Done record. Task 1 is the phase review for both parts, because Phase 9 may add kernel contracts (Task 2) and creates and moves packages. Part B opens with an entry check instead of a second review. This plan does not bump versions, publish, or edit released `/docs`; those wait for Phase 11. Package READMEs, `docs/next/` pages, and `CHANGELOG.md` `## [Unreleased]` entries are written as each task lands. `hooks-json` is already done (plan 147). Workflows are Phase 16.
