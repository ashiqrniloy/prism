# Phase 11 Part O10 — Multi-session recall: passive plus tools, aggregation-ready facts, and a live held-out acceptance

## Objectives

- Make multi-session recall work. **Owner decision (2026-10-23): multi-session success is required for 0.13.0.** A multi-session question needs evidence from several past conversations combined: counting, totalling, listing or comparing.
- Measure the product's real delivery shape for the first time: passive injection **and** the memory tools in the same session. Every benchmark arm so far has had one or the other. Add one domain-neutral cue that tells the agent when passive delivery showed only part of what matched.
- Make the extractor reliable and affordable enough to run:
  - its own output budget and reasoning level;
  - truncation detected, classified and repaired;
  - failure reasons counted instead of hidden;
  - prompt overhead measured and trimmed where it is shown to be waste.
- Make extracted facts **aggregation-ready**:
  - one fact per instance;
  - keys that never supersede a sibling instance;
  - generic category keywords so a question's wording reaches facts phrased differently;
  - a date on every event.
- Diagnose multi-session failures offline before spending, by evidence dispersion and lexical reachability.
- Run a **staged development screen**: the cheap read-side lever first, the paid extraction lever only if the first misses. Allow at most two bounded, evidence-led development iterations.
- Run one **live held-out acceptance** of the selected configuration, with every adjustment from this plan, on a fresh draw that no earlier plan has read. Pre-registered target: **multi-session ≥ 60%, and no other ability regresses**.

## Expected Outcome

- `retrieval-diagnostics.mjs --multi-session` reports, per multi-session question:
  - needed rounds;
  - sessions spanned;
  - each needed round's uncapped question-only rank;
  - lexical reachability;
  - on a store with facts: fact coverage and supersession loss.
- When passive injection shows fewer eligible notes than matched, it says so in one line and names `memory.recall`/`memory.read` when those tools are registered for the session. Benchmark arms `fabric-x-tools` and `fabric-xc-tools` run passive injection with the memory tools visible.
- `promote.maxOutputTokens` and `promote.thinkingLevel` configure the extractor call. Truncation becomes the reason code `output_truncated`, repaired at most once. `FabricConsolidationReport` counts failures by reason.
- The extractor prompt writes aggregation-ready facts (one per instance, instance-safe keys, category keywords, dated events). The coding consolidation and lifecycle suites are unchanged.
- Fresh draws are committed:
  - `heldout-v3.json`, label-free, never read before Task 9: multi-session 40, knowledge-update 20, temporal-reasoning 20, single-session-user 14, single-session-assistant 6;
  - `screen-ms-v1.json`, development only: multi-session 30, plus screen-v1's 30 non-multi-session ids.
- A development screen verdict. Then a held-out v3 verdict for the selected arm against `fabric-x` and a fresh `full` reference, with:
  - the multi-session target;
  - per-ability non-regression;
  - an F13 188.10 evidence column;
  - a documented recommended conversational profile, if the target is met.
