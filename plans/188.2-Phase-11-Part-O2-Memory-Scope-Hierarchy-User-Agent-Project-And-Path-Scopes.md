# Phase 11 Part O.2 — memory scope hierarchy: user, agent, project, and path scopes with union recall

## Objectives

- Replace the fabric's single fixed scope with a hierarchy. Today every note lands in one `{tenantId, resourceId, threadId}` bucket, `prism/fabric/default` unless the host varies it (`fabric/src/config.ts` `DEFAULT_FABRIC_SCOPE`), so project A's facts leak into project B and a user preference cannot follow the user into a new project (defect D1).
  ```text
  user      who the person is, their preferences, their environment (shell, OS, tools)
  agent     general procedures and lessons that hold in any project
  project   architecture, conventions, decisions and their reasons, owner calls
    path    notes that apply to a subtree (applies_to globs)
  session   observational memory only; never long-term
  ```
- Give each project a stable identity, so worktrees and moved folders share one project's memory.
- Recall reads the union of the active scopes with a scope prior and per-scope budgets. When the same key appears in two scopes, the narrower one wins.
- Run the read-only assumption check for the whole memory-lifecycle series (plans 188.2–188.6).

**Evidence** (owner-approved memory-lifecycle analysis, 2026-10-19):

- **Scope is retrieval context.** Recall is best when the retrieval context matches the encoding context: encoding specificity (Tulving & Thomson 1973), context-dependent memory (Godden & Baddeley 1975), the temporal context model (Howard & Kahana 2002).
- **Precision first.** Agents follow what they retrieve: a note from the wrong context gets replicated, and its errors spread (Xiong et al. 2025, arXiv 2505.16067). So a note is stored at the narrowest plausible scope.
- **Read-time union is the closest existing practice.** Mem0 scopes writes by user, agent, session, and org and unions them at read time. Claude Code layers user, project, and directory memory files.
- **No public benchmark tests user/project/path scoping.** Plan 188.6 builds the longitudinal multi-project suite that measures leakage.

## Expected Outcome

- Config `scopes` replaces `scope`:
  ```ts
  memoryFabric({
    tools: { root: "~/.prism/memory" },
    scopes: { tenantId: "prism", user: true, agent: true, project: { root: "." } },
  });
  ```
  - Resource ids: `user`, `agent`, `projects/<slug>--<id8>`. Under plan 188.1's layout they map to `notes/<tenant>/user/…`, `notes/<tenant>/agent/…`, and `notes/<tenant>/projects/<slug>--<id8>/…`.
  - `scope` and `DEFAULT_FABRIC_SCOPE` are deleted with no alias.
- **Project identity:**
  - From the git remote URL, normalised (scheme, credentials, and a trailing `.git` stripped; host lowercased), read from `.git/config` with worktree `gitdir`/`commondir` followed.
  - Else the real path of the git top level, else the real path of the root. Task 1 (d) found no no-subprocess way to read the root commit, so there is no root-commit source.
  - `projects/<slug>--<id8>/project.md` records the identity source and every root seen. A worktree or a moved folder adds a root and keeps the id.
- Notes carry a scope; `path`-scoped notes carry `applies_to` globs relative to the project root.
- The new kind `preference` is stored under `user/preferences/` by default.
- **Default write scope by kind:**

  | Kind | Default scope |
  |---|---|
  | `preference` | user |
  | `fact` | project |
  | `procedure` | project |
  | `episode` | project |
  | `file` | project |

  `memory.insert` takes an explicit `scope` and `applies_to`. Its description states the precision-first rule.
- **Recall** queries every active scope, fuses the results with RRF, applies a bounded scope prior (path > project > agent > user), and drops a wider-scope hit whose `key` matches a narrower-scope hit. Every hit is labelled with its scope.
- **The memory directory** reports counts and topics per scope.
- **Fail closed:**
  - A note never crosses projects. The leakage test seeds project A and recalls from project B.
  - Without a resolvable project root, the project scope is off, with a status note, and only user and agent scopes are active.

**0.13.0 release path — plan 188.2, step 4c, after 188.1 and before 188.3.** Owner decision 2026-10-19: the memory-lifecycle design (scope hierarchy, session-end consolidation, two-strength retention, delivery tiers, lifecycle evaluation) ships in 0.13.0 as plans 188.2–188.6, all before plan 189.
