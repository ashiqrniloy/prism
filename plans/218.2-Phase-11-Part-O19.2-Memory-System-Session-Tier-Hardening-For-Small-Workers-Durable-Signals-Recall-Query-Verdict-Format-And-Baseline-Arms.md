# Phase 11 Part O19.2 — Memory system: session-tier hardening for small workers (durable signals, recall query, verdict format, baseline arms)

## Objectives

- Act on the memory evaluation of 2026-11-13 (owner: "all the 8 points … I want to cover"; design §14). This plan carries the findings that live in the session tiers and in the gate harness. The findings about Rehearsal, trust by use and plan breadth are amendments to plans 219–223.
- Make the session tiers hold up when the memory worker is a small model:
  - STM records what a later tier needs as **structured fields**, so salience and protections stop reading English regular expressions (finding 4);
  - a user constraint or preference is marked **durable** at encoding, scope-blind, so WM cannot drop it for the episode and Rehearsal sees it whatever WM decided (findings 1 and 4);
  - errors and failed checks keep their evidence **by rule**, not by the worker guessing what will matter (finding 6);
  - WM gives its verdicts in **one compact call** over short ordinals, with the records code already protects settled before the model is asked (finding 3);
  - a record WM discarded is **findable by a query**, not only by an id the agent no longer sees (finding 2).
- Give every later gate the **cheap baselines** the literature says are strong, a reading at the **shipped triggers**, and a **whole-run cost** row (finding 7).
- Decide each product change on a cheap, mechanical **worker replay screen** that runs the small worker models alone, before any agent-level paid run.

## Expected Outcome

- `scripts/memory-bench/worker-replay/` replays frozen STM and WM requests through live small worker models and scores them against annotations with no judge model. Its baseline is recorded before any product change.
- `record_event` carries `status`, `corrects`, `durable` and `resolves`. `salience.ts` and `protections.ts` read them. The English patterns stay only if the replay shows the fields lose recall (Task 2).
- Protections follow content: a durable constraint is protected for the episode, a request until an outcome resolves it, an error until a passed outcome resolves it.
- An `error` event, a failed `outcome` and a durable `statement` get a capped verbatim chunk by rule when the worker attached none.
- WM answers with one `judge` call over ordinals, or keeps today's four tools: the replay decides, and the loser is deleted.
- `recall` takes `query` and searches this session's STM and WM descriptions, tombstones included. The memory block says how many records were discarded and how to search them.
- The gate harness has `fold` and `llm-summary` arms built from two packages that already ship, a `long-horizon` family that runs at the shipped triggers, and whole-run tokens per successful task in every report.
- Evidence in `docs/_evidence/memory-bench/218.2/`.

This implements roadmap Phase 11 "Memory model", the amendment of 2026-11-13, inside plan 218: after plan 218.1 Task 3 Step 1 (the WM engagement probe, running on 2026-11-13), and before plan 218.1 Task 3 Step 2 and plan 218 Task 6 resume. Both of those read the product this plan changes, so they wait for it. **No review task:** every product change is internal to `@arnilo/prism-memory-system` (worker tools, the ledger, the session `recall` tool); the harness arms use the `compaction` slot and the `context.build` hook through two shipped packages; no kernel contract, package or subpath is added or moved. No version bump and no publish.

**Constraints already known:**

- The STM instruction stays at or under 2,100 characters (owner, 2026-11-11: "do not get too bloated"; `session/__tests__/stm.test.ts:80`). New guidance goes into tool schema descriptions, not the instruction.
- No WM or STM trigger is lowered for a benchmark (owner, 2026-11-13).
- Live runs use the providers and models the owner names in each gate record, never `openrouter/free`.
- While the plan 218.1 probe unit (`prism-218-1-wm-probe.service`) runs, no file under `packages/` or `scripts/memory-bench/` changes: Task 1 starts after it ends.

- [ ] Task 5: WM verdicts in one call over ordinals, with protected records settled first
  - Acceptance Criteria:
    - Functional: **Settled before the model.** Records protected as `constraint`, `task_state`, `unresolved_error` or `open_question` are kept as WM events by code, with the protection as the reason. The WM request shows them under "Already kept" and asks no verdict for them. Records protected as `fact` or `needed_later` still go to the model, because a summary may absorb them.
    - Functional: **`judge` tool.** One call carries every verdict for the batch. Records are shown as `r1…rN` and current WM items as `w1…wM`; the package maps ordinals to ids.

      ```json
      { "keep": [{ "r": 4, "reason": "task 3 reads this path", "neededLater": "Task 3" }],

        "facts": [{ "text": "…", "support": [4, "w1"], "relevance": "high" }] }
      ```

      - the share of records given a verdict is no lower;

      - and output tokens per record fall by at least 30%, or refused calls fall.
