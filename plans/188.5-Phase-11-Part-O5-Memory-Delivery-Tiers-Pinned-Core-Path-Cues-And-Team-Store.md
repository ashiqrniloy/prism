# Phase 11 Part O.5 — memory delivery tiers: pinned core, path cues, and the team project store

## Objectives

- Get the right note to the agent at the right time, in three tiers that follow the encoding-specificity principle:
  1. **Pinned core.** Always in the prompt prefix and stable for caching: a small curated summary for the user and one for the project (top notes by storage strength S, about 300–600 tokens). It is rebuilt only when consolidation or maintenance changes it. The existing directory block (counts and topics) stays as the map for everything else.
  2. **Cue injection.** When a tool reads or edits a path matching a note's `applies_to`, that note is injected once at the tail. Topic cues already work through `inject` with the lexical floor (plan 188.1 Task 3) and now use the union recall (plan 188.2 Task 4).
  3. **On demand.** `memory.recall` with multiple queries (plan 188.1 Task 3).
- Add the optional team project store: `<repo>/.prism/memory/`, checked in and reviewed in PRs. It holds the team's shared project notes, separate from a person's private notes (the split between a checked-in CLAUDE.md and a personal one). Notes move into it only with human approval.

**Evidence** (owner-approved memory-lifecycle analysis, 2026-10-19):

- **Encoding specificity and context reinstatement** (Tulving & Thomson 1973; Godden & Baddeley 1975). A cue matching the encoding context brings back the memory, so path cues inject path notes when that path is touched.
- **Agents often fail to ask for memory they need.** Passive injection needs a precision floor (plan 188's injection-precision measurements). Hence a small, high-S core plus narrow cues rather than broad injection.
- **Prompt-cache parity is a release goal** (plan 184). The core block must be byte-identical between consolidations; it is placed in the prefix and rebuilt only on maintenance.
- **Practice.** Claude Code's layered memory files (user, project, nested directories loaded just in time) and plan 190's nested `AGENTS.md` loading show the tiered pattern. MemGPT/Letta core memory blocks (Packer et al. 2023) are the always-present tier.

## Expected Outcome

- Config:
  ```ts
  core: false | { maxTokens?: number /* 600, hard 1000 */, scopes?: ("user" | "project")[] /* both */ },
  cues: false | { budgetTokens?: number /* 300 */, maxPerTurn?: number /* 2 */ },
  team: false | { dir?: string /* ".prism/memory" */, write?: "approval" | "off" /* "approval" */ },
  ```
  - Defaults: `core` on, `cues` on, `team` off. Plan 188.6 confirms or changes them with paired evidence. Core and cues make no model call.
- **The core block.** One `fabric-core` prefix block, after the working-memory and directory blocks:
  - user-scope preferences and facts first, then project notes
  - each line `[id] text`, ordered by S, verified only, never archived
  - pinned notes (plan 188.4 Task 4) always included
  - persisted as derived `core.md` per scope (markdown store), so a person can see exactly what the agent always sees
  - rebuilt only by `maintain()`, by consolidation, or by an edit or pin of an included note
  - a turn with no such change sends byte-identical bytes
- **Cue injection.** After a file tool touches a path (plan 188.2 Task 4's tracker):
  - the next `context.build` injects up to `maxPerTurn` path-scoped notes whose `applies_to` matches it and which were not yet injected in this session
  - placed at the tail through `withTailContext` (`core/src/tail-context.ts:6-39`), within `budgetTokens`
  - deduplicated against the core, OM, visible file reads, and earlier injections (existing cross-source dedup)
- **The team store.**
  - With `team` on and the directory present, recall reads it as the `team` scope, between project and agent priority.
  - Its notes are loaded through the trust scan (flagged → quarantined candidates, plan 188.1 Task 6).
  - `memory:share { id }` stages a copy of a verified project note into the team directory only after a `host.ui` approval. With `write: "off"`, the command is refused.
  - The agent never writes the team store through `memory.insert`.

## Compromises Made

- **No separate core generation counter** (Task 1). The core caches on `directory.ts`'s existing
  `memoryWriteVersion` write counter instead of a new counter bumped by `maintain()` and
  `consolidation`. Every write path already bumps it, and recomputing lazily on the next
  `context.build` means `lifecycle/maintain.ts` and `consolidation/index.ts` needed no edit. Cost: the
  first build after any write pays the recompute, which is where it would have been paid anyway.
- **The team store is a scope, not a storage level** (Task 3). `team` joins `FabricScopeLevel` for the
  prior and shadowing order, but it reaches recall through a new `readOnlyScopes` option rather than
  `scopes.active`. Read-only-to-tools, no capacity, no widening, and no maintenance then follow from the
  existing write path instead of from a check that could be forgotten. Cost: one more option a caller can
  misuse (a writable scope in `readOnlyScopes` would be recall-visible but never maintained).
- **The team index is the only file moved out of the repository.** `index.md`, `log.md`, and two dotfile
  caches (`.index-files.json`, `.state.json`) still live in `.prism/memory/`. Moving the caches needs a
  memory-core option outside this plan's file list; the two human-facing files are the reviewed artefact.
- **The cue index is bounded to 4,000 path notes** per open (8 pages × 500 rows). A project with more
  path-scoped notes than that can silently miss matches. Bounded to keep a turn's cost predictable; the
  bound is named in Further Actions.
- **The cue appends through the semantic tail, one tier at a time.** Topic injection and cues share one
  tail block, and the injected set is per session, so a cue shows on the turn its path is first touched
  and not again — a re-read of the same file in a later session shows it once more. That is the
  designed "once per session", and it keeps the tail byte-stable on quiet turns.
- **No end-to-end cue test in `package.test.ts`** (Task 2). The harness has no `read` tool, and adding one
  to the package suite was out of scope; the tier is covered by the 8 unit cases plus the agent-level
  demonstration in `examples/memory-lifecycle.ts` and the prefix-stability test (Task 4).
- **Task 4 drives the tiers through the mock provider.** The example has to run a real agent to reach the
  tail at all, so it adds a scripted provider, a scripted host UI, and a two-line `read` tool. It stays
  network-free and makes no model call, but it is no longer a pure package-level script.
- **Kernel budgets were rebaselined five times** (+489/+1381, +396/+1259, +549/+1775, +254/+819, and
  +264/+629 for the Further Action 5 root CHANGELOG entry), each attributed to a root CHANGELOG entry. No
