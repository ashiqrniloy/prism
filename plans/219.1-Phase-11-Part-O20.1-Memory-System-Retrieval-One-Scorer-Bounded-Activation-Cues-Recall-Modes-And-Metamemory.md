## Objectives

- Make LTM retrieval robust without embeddings (owner, 2026-10-24: memory is not RAG-based). The design is in `docs/_evidence/memory-model/design.md` §5.11 (owner decision 2026-11-08, after the retrieval review).
- Fix the defects the review found in today's ranking (design §5.11, D1–D7):
  - priors swamp relevance with several scopes;
  - priors do nothing with one scope;
  - Postgres does not index the keys and ranks differently from SQLite;
  - order and confidence use different signals;
  - two other analyzers (ASCII-only and Postgres `english`) disagree with the shared one, and text without spaces is unsearchable.
- Build the retrieval pipeline of design §5.11 in stages:
  - one analyzer and one BM25F scorer across stores (I14);
  - one bounded activation score (I13);
  - query cues (time, context);
  - an association index with spreading activation and episode completion (I15);
  - recall modes chosen by question type;
  - calibrated confidence with partial results (metamemory).
- Measure it at gate M-T (rows T1–T8, pre-registered by plan 216 Task 2): offline first, then one paid development screen. Give the plan 210 retrieval rows that are held or unmeasured their verdicts.

## Expected Outcome

- `@arnilo/prism-memory-core` has one analyzer (`analyzeLexical`) with Unicode word segmentation. Every store adapter (SQLite, Postgres, the markdown index and the in-memory store) returns candidates with field term counts. One TypeScript BM25F scorer ranks them, so the ordered results are identical across adapters on the parity fixture. `tokenizeLexical` and Postgres `text_tsv` are retired.
- `memory.recall` ranks by one activation score:
  - relevance comes first;
  - scope, strength, decay, time, priming and association terms are bounded to `ltm.retrieval.priorBand` (default 0.1);
  - one scope and several scopes behave the same.
- The tool takes `mode: lookup | gather | chronology | history`. The mode is inferred deterministically when absent.
- Every result states `confidence: answer | partial | none`. A partial result names the matched terms, the missing terms and up to three suggested cue terms.
- An association index is derived from cue entities, links, provenance and episode membership. It is disposable and holds no concept, claim or schema.
- `scripts/memory-bench/retrieval-bench.mjs` reports candidate recall, shown evidence coverage and all-required coverage per ability, plus the paraphrase, non-English, parity and abstention sets.
- Gate M-T verdicts and the plan 210 row dispositions are in `docs/_evidence/memory-bench/219.1/`.

This implements roadmap Phase 11 "Memory model", the retrieval part, after plan 219 and before plan 220. It is numbered 219.1 because it is inserted between them: it needs plan 219's episode kind, Rehearsal-written cues and store snapshots, and plan 220's priming plugs into its activation score.

**Review task included** (Task 1). The plan changes a public `@arnilo/prism-memory-core` contract (`VectorStore.lexicalQuery`), the Postgres schema and the recall tool's input and output. It adds no kernel contract.

**Not in this plan:**

- embeddings: `retrieval.hybrid` is removed by plan 210 Task 7, and the owner's lexical-only decision stands;
- the ontology: concepts and claims are the wiki's (design §5.10);
- writing the cue fields: plan 219 Task 2 adds them to Rehearsal's writes, and this plan indexes and uses them;
- Sleep's conflict records: plan 221 Task 3 writes them in the shape Task 7 here reads;
- no version bump and no publish.

**Relation to plan 210's wave 1 removals.** Plan 210 Task 7 removes `timeline` (resolved exchange dates, `from`/`to` windows, time order), `write.keyword-enrichment` and `recall.supersession-hint`. Wave 1 measured them negative, each on one 12-question ability stratum. This plan does not restore them by name or config. Its time cue (Task 5) and its use of Rehearsal-written cues (Task 3) are different mechanisms, and each must earn its place through its own leave-one-out arm at gate M-T.

- [ ] Task 5: Query cues — time and context reinstatement
  - Acceptance Criteria:
    - Functional: **Time cue.** A deterministic parser turns time expressions in the query into an interval relative to the session clock. Examples: "last spring", "in March", "two weeks ago", "before the migration" when it names an episode title. It reuses whatever period code plan 210 Task 7 left (Task 1 finding), or a new module.
      - The interval feeds the `time` activation term as a proximity prior over the note's time: an episode's `startedAt`/`endedAt`, the note's `when` cue, or else its ingest time. It never feeds a hard filter, so a wrong parse costs rank, not recall.
      - Explicit `from`/`to` on episodes (plan 219 Task 1) stay hard filters.
    - Functional: **Context cue** (`ltm.retrieval.context`, default on; its leave-one-out arm `RT-context` decides the default at gate M-T). Tool recall adds the current episode scope's terms and the touched paths' segments as a low-weight query field (weight 0.3, inside the band). This uses the same scope text that passive delivery already uses, with no new read.
    - Functional: **Visibility.** The recall output names the interval it applied (`time≈2026-03-01..2026-05-31`), so the agent can see and correct it with explicit options.
    - Performance: Parsing is pure and under 1 ms per query; no store query is added.
