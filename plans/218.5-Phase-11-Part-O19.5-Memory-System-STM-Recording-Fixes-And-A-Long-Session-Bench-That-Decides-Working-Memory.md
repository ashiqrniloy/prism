> **Why the screen cannot answer this.** STM grows about 190 description tokens per task (range 140–326, 5.7 records per task, over 14 replayed STM ledgers). Session-Bench v3 sessions run 8–14 tasks, and their STM pool reached at most about 3,100 tokens. The compaction block holds `min(20,000, 30% × input cap)` description tokens (`config.ts:77`). At W = 32K that is 8,985, reached at about **task 47** on average and about **task 28** in the densest session. At large windows the pool is 20,000, reached at about task 105 (61 at the densest). Past the pool, `boundMemoryPayload` (`memory-bounds.ts:21-45`) leaves records out, and the order it uses is itself weak. It removes the lowest relevance first, then the **smallest** first (`memory-bounds.ts:32`). 817 of the 901 replayed records are `medium`, so short user rules are evicted before long assistant action lines. The screen measured none of this.

## Objectives

- Land STM's recording fixes 1–3 (owner, 2026-11-22), prove them on a worker probe and on replays, and keep them only on a measured gain.
- Land the candidate product changes the long run compares:
  - WM's seven mechanical fixes from the WM critique;
  - an STM eviction order that protects durable records and user statements.
- Build a project-owned long-session variant of Session-Bench (W = 32K, 100 tasks per session), so more than half of each session runs under eviction. Keep v3's environment, jobs and guardrails, and never edit v3's frozen core files.
- Pre-register the arms, the distance buckets (before and after the pool overflows), a three-way WM rule (keep / drop / owner decides), the cost rule and an STM-at-length finding, all frozen before any paid call.
- Run a paid pilot, then the full run, on the owner's word, under the screen's discipline: a worker fault leaves no row, a usage limit stops the run, health is watched. Hand the verdict to plan 218.4.

## Expected Outcome

- STM records a user's value change as its own statement that supersedes the old record and inherits its rank, and keeps short user messages verbatim. The worker probe and the replays show where this helps, in the variant the tests picked. The memory-system compat baseline is regenerated, and its diff is attributed.
- WM's mechanical fixes are in the product. The STM eviction candidate sits behind one config key whose default is the current order until this plan's verdict.
- `scripts/memory-bench/session-bench-long/` generates 3 families × 12 sessions (6 dev, 3 heldout-a, 3 heldout-b per family) that regenerate byte for byte from their own seed and partition file. v3's pins do not change.
- The offline run passes G1–G11 on every dev session; G11 is new and checks that the pool overflows before the first "after" dependent.
- `docs/_evidence/memory-bench/218.5/` holds the gate record, the probe, the pilot and run evidence (ids, counts, hashes and per-bucket rates only) and a README with the verdict.
- Plan 218.4 either runs or is closed, and the decision is recorded in the gate and in Task 8's notes.

This plan changes the memory package's behaviour and adds config keys (Tasks 1 and 3). It changes no kernel contract, so there is no kernel phase review; Task 2 is a design review that measures pressure and the overflow risk and records the owner's open decisions before any bench code lands. Nothing is published and the version does not change. Package docs change in the memory-system README; `/docs` kernel pages do not. Every paid call (probe, replays, pilot, run) needs the owner's word, and every bench rule change is a new hash.

    - Functional:
      - **Fix 1, user messages word for word.** Before the model reads a batch, each user message of at most `stm.verbatimUserChars` characters (default 2,000; whitespace collapsed; `0` off) is recorded as one `request` record, `User said: …`. The record:
        - is attributed to the user, relevance `high`, and marked with the new `MemoryObservation.verbatim`;
        - renders as `request (verbatim):`;

## Cost and power (estimate for Task 2's owner decisions)

These are upper bounds from the screen's whole-run tokens per task: `memory-off-llm` 233K, `STM-only` 265K, `STM+WM` 337K, `mem0` 188K, at 17–18.5K-token artifacts. Smaller artifacts lower main-agent input per call, but STM's block grows over the session, so late tasks compact more often; Task 8 reports cost per bucket. The `STM-only-protect` and `STM+WM-deterministic` arms are estimated at STM-only's rate.

| Design | Tasks per arm | off-llm | STM-only | STM-protect | STM+WM | WM-determ. | Total (5 arms) | + mem0 | + calibration |
|---|---|---|---|---|---|---|---|---|---|
| 12 × 100 (recommended) | 1,200 | 0.28B | 0.32B | 0.32B | 0.40B | 0.32B | **1.64B** | +0.23B | +0.10B |
| 12 × 100 × 2 repetitions | 2,400 | 0.56B | 0.64B | 0.64B | 0.81B | 0.64B | 3.28B | +0.45B | +0.10B |

**Wall time.** The screen ran about 100 s per task, so a 100-task job takes about 3 h. The 60 jobs at concurrency 6 take about 30–35 h, and 2 repetitions about 60–70 h.

**Power.** The screen's STM-only → STM+WM interval was ±0.09 at N = 35, with about 4.2 dependency checks per session, which gives a per-session SD of about 0.27. With about 10 or more `after` dependency checks per session, and if within-session noise dominates, the SD falls to about 0.17. That supports within-session noise dominating: replays flipped 4 of 12 STM D4 outcomes. The 80% detectable effect is then about 0.14 at N = 12. Two repetitions per session cut the within-session part, to about 0.10–0.11. A session-level effect would make both larger. Task 7's spread replaces this estimate.
