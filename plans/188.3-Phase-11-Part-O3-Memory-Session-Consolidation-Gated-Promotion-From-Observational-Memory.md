# Phase 11 Part O.3 — session consolidation: gated, typed, scoped promotion from observational memory

## Objectives

- Replace "every clean reflection becomes a `fact` candidate on the next turn" (`fabric/src/promote.ts` `runFabricPromotion`) with consolidation in the style of sleep: offline, over many turns of material at once, selective. Defects addressed:
  - D3: no selection criteria.
  - D11: everything is typed `fact`.
  - D12: promotion runs per turn, before anyone can judge whether a fact outlives its task.
  - D4 in general: evidence that OM later supersedes reopens the note.
- Gather candidates from every signal OM and the session already record:
  - reflections
  - task-state decisions
  - observations rated `high` or `critical`
  - explicit "remember / always / never / I prefer" statements
  - user corrections
  - outcomes: a test command that passed, a commit, an approval
- **One extractor model call per consolidation pass.** It turns candidates into atomic notes with a type, a proposed scope (plan 188.2), keys and aliases, and evidence ids.
- Score each candidate and gate it:
  `P = explicit + correction + outcome + recurrence + generality − ephemerality − derivability − duplicate`.
  Only notes above `minScore` are written. They go through the existing reconcile path (ADD / UPDATE / SUPERSEDE / NOOP) as candidates with provenance and scores.
- **Narrowing by contradiction.** A candidate that contradicts a user- or agent-scope note becomes a project exception note (`overrides`), and the wider note's contradiction count rises. Plan 188.4's maintenance pass supersedes a wider note contradicted in k projects.
- Episodes: one short note per task segment, with its outcome, for plan 188.4 to merge later.

**Evidence** (owner-approved memory-lifecycle analysis, 2026-10-19):

- **Complementary learning systems** (McClelland, McNaughton & O'Reilly 1995; Kumaran, Hassabis & McClelland 2016). A fast episodic store and a slow structured store, linked by offline replay. OM is the fast store and the fabric is the slow one, so consolidation runs over a block of experience, not per event.
- **Consolidate what generalises** (Sun et al., *Nat. Neurosci.* 2023). Transferring unpredictable detail to the slow store causes overfitting. Hence the generality and ephemerality terms.
- **Prioritised replay: gain × need** (Mattar & Daw 2018). Rank by expected behavioural benefit times the probability of future need.
- **Synaptic and behavioural tagging** (Frey & Morris 1997; Moncada & Viola 2007). A weak trace is kept when a significant event follows. Hence outcome tags.
- **Prediction error drives encoding** (Lisman & Grace 2005). Surprise-gated memorisation also appears in Titans (Behrouz et al. 2025). Hence corrections score highest.
- **Spacing** (Cepeda et al. 2006). Recurrence across sessions outweighs repetition within one.
- **Selective addition works.** Selective addition plus deletion gave about +10 points absolute over add-everything (Xiong et al. 2025, arXiv 2505.16067).
- **The form of a stored record decides whether memory helps a coding agent.** Memory systems storing transcript-like records sat at or below the memory-off baseline in 11 of 12 pairings, while frozen, verified experience helped (VibeMemBench, arXiv 2609.23570; contested). Hence atomic, abstracted notes.
- **Offline consolidation can cut tokens and calls by large factors without losing accuracy** (LightMem, ICLR 2026; Letta sleep-time compute).
- **Do not store what the repository already records.** This is the derivability term; Claude Code's memory guidance follows the same rule.

## Expected Outcome

- Config `promote` is reshaped (replacing `promote.observational`):
  ```ts
  promote: false | {
    model?: "provider/model",     // default: the agent's model
    minScore?: number,            // default 0.5 (provisional until plan 188.6)
    weights?: { explicit, correction, outcome, recurrence, generality, ephemerality, derivability, duplicate },
    maxCandidates?: number,       // default 48 per pass
    minTurnsBetween?: number,     // default 8
    derivableFrom?: string[],     // default ["AGENTS.md", "README.md", "package.json", "CLAUDE.md"]
    verifyAfterUses?: number,     // kept until plan 188.4 moves it to lifecycle
    archiveAfterDays?: number,    // kept until plan 188.4 retires it
  }
  ```
  - Default `false`: no model call. Plan 188.6 decides whether to turn it on by default, from paired evidence.
- **Triggers.** Final form follows plan 188.2 Task 1 (b). The planned form:
  1. A background pass at `turn.completed` when OM has recorded new reflections or task-state decisions since the cursor and at least `minTurnsBetween` turns have passed.
  2. `memory:consolidate` (command) and `fabric.consolidate(session)` (host API), which a host runs before `session.close()` to consolidate the tail.
  3. On `session.opened` with `restored: true`, a pass over material the cursor has not covered.
- **Each pass:**
  - gathers candidates (no model call)
  - makes one extractor call
  - scores deterministically
  - reconciles each accepted note, making at most one decider call per note when the decider is configured, as today
  - writes accepted notes as `status: candidate` with `generated.by: promotion` (plan 188.1 Task 6), `sources[]` evidence ids, and `prism.promotion: { score, signals }`
- Reflection supersession reopens notes. A note whose evidence reflections are all superseded gets `reconsolidate: true`, and the next pass re-extracts it with the new evidence, keeping its id.
- `memory:status` reports, per pass: candidates gathered, accepted, rejected by reason (score, ephemeral, derivable, duplicate, trust scan, secret), and model calls.

- [x] Task 3: Scoring and the promotion gate
  - Notes (executed 2026-10-19):
    - **`packages/memory/fabric/src/consolidation/score.ts` (new)**: `scorePromotion(note, context) → { score, signals, accepted, reason? }`. Pure and synchronous — no store, no model, no filesystem. `context` carries what the pass resolved: `candidates` (the gathered candidates `note.evidence` maps to), `sessions` (distinct sessions covering them and any UPDATE target's `sources[]`), `existing` (same-scope active notes for the duplicate term), `derivable` (from `loadDerivableSources`), plus `weights`, `minScore`, `scratchDir`. Keeping the lookups outside keeps the gate testable and lets Task 5 reuse the extractor's already-recalled notes.
    - **Weights are data**: `DEFAULT_PROMOTION_WEIGHTS` (`explicit 1`, `correction 1`, `outcome 0.5`, `recurrence 0.5`, `generality 0.5`, `ephemerality −1`, `derivability −1`, `duplicate −0.5`), `DEFAULT_PROMOTION_MIN_SCORE` (0.5), `DEFAULT_RECURRENCE_SATURATION` (4), `DERIVABLE_COVERAGE` (0.9), `MAX_DERIVABLE_FILE_BYTES` (64 KiB), `MAX_DERIVABLE_FILES` (16). Non-finite weights or `minScore` raise a `RangeError`; the resolved config validates bounds (Task 5).
    - **`explicit`/`correction` are cross-checked**, not trusted: the flag survives only when the cited candidates include a candidate of that source, so an extractor claiming `explicit` over a plain observation scores 0.
    - **`outcome`** is 1 when any cited candidate carries `signals.outcome === 1`.
    - **`recurrence`**: the plan's literal `log2(1 + distinct sessions)` capped at 1 saturates at a single session (`log2 2 = 1`), which would make the term a constant and defeat "spacing outweighs repetition within one". One session scores 0, repeats inside a session add nothing, four or more score 1.

The reason string is returned for diagnostics.

## Compromises Made

- **The extractor sees reconsolidating notes as existing notes, not candidates.** Candidates are evidence text (explicit statements, reflections, observations, decisions) and the extractor already receives up to 12 existing notes per scope. The old note text is therefore shown among the existing notes, and a returned note updates it only when `key`, kind and scope match. A keyless reconsolidating note cannot be matched and is retired after the pass, per Task 4's "nothing for its key" rule.
- **No `duplicate` rejection reason.** Task 3's gate treats duplicate as a weighted term that lowers the score; the reason codes are `score`, `ephemeral`, `derivable` (Task 3) plus `trust` and `secret` (Task 2). `memory:status` reports exactly those. A near-duplicate rejection is visible as `score`.
- **Two branch reads per triggered pass.** The turn trigger reads `session.entries()` to decide whether material exists (the "no new material starts no task" rule), and the pass reads the branch again. Both are bounded, and only run when `promote` is enabled and the turn threshold is met.
- **The turn counter is in memory.** Only the cursor and the last report persist in package state; a restored session starts its counter at 0 and relies on the `session.opened` catch-up pass, which the plan asked for.
- **`promote: false` still resolves lifecycle defaults.** `verifyAfterUses: 2` and `archiveAfterDays: 30` keep governing cited-note verification and candidate archiving when consolidation is off, as they did after Task 4; `false` specifically means no extractor call.
- **Internal pass symbols appear in the compat baseline.** The release gate's surface extractor walks every emitted `.d.ts`, so `runConsolidationPass`, the lease and the material check show up alongside the real public additions (`MemoryFabric.consolidate`, its types, the report, the reshaped config). They are not reachable through the package entry point.
