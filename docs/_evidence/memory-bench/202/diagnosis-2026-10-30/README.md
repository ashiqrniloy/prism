# Memory efficacy diagnosis and recommended next steps — 2026-10-30

This is an offline audit of the closed Muse 1.3 screen, current memory implementation, and plan 202 Tasks 5–17. It makes **zero model calls**, changes no product behavior, and leaves the owner closure intact. `audit.json` verifies the hashes of all 23 accepted reports and contains reproducible cohort ids, per-suite failure counts, paired comparisons and two direct ingestion/measurement reproductions. The original accepted report is preserved, including its statistics; this document corrects its interpretation, not its observations.

## Conclusions

The current evidence does not support either “memory is generally effective” or “the memory architecture is fundamentally broken.” It demonstrates a lexical, verbatim-exchange conversational preset with real delivery/answering weaknesses, alongside important benchmark defects. Fix the benchmark prerequisites first, then execute the relevant **existing** plan tasks with checkpoints. Do not implement every remaining capability before reassessing, replace lexical memory with embeddings, or add fact extraction because of the current stage labels.

Two earlier conclusions need correction: MemoryAgentBench's 0% cannot diagnose conflict handling when historical facts were never archived, and LoCoMo's 13 fine-selection labels cannot establish failure to select fine evidence when its ids are incomparable. Broad cross-model lever decisions based on those labels must remain provisional.

## Observations, mechanisms and confidence

| Finding | Evidence | Interpretation / confidence |
|---|---|---|
| MAB memory is given no historical exchange notes | `datasets.mjs:467–485` turns each context line into a user-only session. `replay.mjs:697–740` imports those sessions through `memory:archive`. `exchanges.ts:83–96` requires a final assistant response. Across the 20 selected dev cases: 118,778 repeated session instances, zero assistant messages, zero exchange pairs. Direct archive reproduction calls `remember` zero times. | **Confirmed adapter/archive contract mismatch.** Conversation archiving behaves as implemented; a fact-list corpus is not a supported exchange fixture. This result must not be used as a real conflict-resolution score. Test supported document/fact ingestion or explicitly supported user-only capture; otherwise mark this suite unsupported. Do not fabricate assistant replies. |
| LoCoMo fine recall is invalid | `extractEvidence` maps message evidence to rounds but retains raw message ids in `fineGoldIds` when no `sourceAnnotations` object exists (`replay.mjs:275–315`). All 60 LoCoMo fine-gold sets have no overlap with round ids. Saved recall contains round ids. Of 13 wrong answers labelled fine-selection gaps, eight recalled every mapped gold round. | **Confirmed granularity bug.** Correct id mapping before interpreting these labels. Recall of a round still does not prove its important sentence was delivered in an excerpt. |
| Candidate failure versus selection failure cannot be separated | `replay.mjs:1178–1185` computes `candidateGold` and `selectedGold` from the identical final recalled-id set. This equality holds for all 210 preset questions. `memory.read` results are not included in the tool-result evidence collector (`:887–898`); query arguments and delivered text are not retained. | **Confirmed observability limitation.** “Candidate gap” means no measured final surfacing, not proof that the search pool lacked the evidence. Existing Task 5/8/13 priorities require better measurements. |
| The tested memory is lexical, not an embedding or extraction system | Every preset report has `retrieval: lexical`, `promote.enabled: false`. `ablations.mjs:78–119` selects the conversational exchange preset; `config.ts:938–944` disables promotion. `semantic: true` is the delivery channel flag, not proof of vector search. | **Confirmed scope.** Improve lexical navigation as planned. The owner's plan explicitly rejects an embedding-first redesign; no such redesign is required by these findings. |
| Much relevant evidence fails to reach the answer | BEAM-100K wrong-answer labels: 11 no surfaced gold, nine partial-evidence, three answer-gap, three abstention, one run-limit; mean recorded round-level fine recall 0.385. BEAM-1M: nine no surfaced gold, 11 partial-evidence, four abstention, two unknown-label cases; mean recorded fine recall 0.218. | **Observed evidence-delivery weakness**, but stage labels are not causal separation of index, ranker and renderer. Inspect candidate pool, top-k and actual excerpts separately. |
| Tool use helps some answers, but can exhaust the answer budget | Explicit `memory.recall` appears in 18/40 BEAM-100K, 32/60 LoCoMo, 21/50 LongMemEval-M and 16/40 BEAM-1M questions. `recallCalls` additionally includes one automatic passive lookup and cannot be read as explicit tool use. Six preset questions hit the eight-turn run limit (1 BEAM-100K, 3 LoCoMo, 2 LongMemEval-M). | **Observed**, not proof of a weak-tool-caller model. Tool memory exceeds passive raw accuracy on four suites; reserve a final answer within the fixed budget, improve navigation/grouping, and measure recovery before changing turn limits. |
| Passive delivery has a finite evidence bottleneck | `context.ts:274–305` searches with the question/task text, takes up to 12 notes within a default ~4,000-token excerpt budget; `recall.ts` defaults explicit recall to a 0.35 similarity floor. Many histories require multiple sessions. | **Credible mechanism**, not measured causal contribution yet. Top-k, lexical mismatch, missing neighbours, excerpt loss and multi-query synthesis must be isolated with oracle ablations. |
| Capacity eviction is not established as the cause | Preset configuration has a 500-note/60K-token project capacity, but the benchmark importer does not explicitly invoke `memory:maintain` on its normal growth schedule. Temporary stores are rebuilt per question and deleted after runs. | **Unproven for these scores.** Do not blame the configured capacity simply because histories are large. Test actual maintenance/archiving in Task 15. Current results do not validate lifelong durability or scale. |

The LoCoMo deficit is real as an answer-quality observation: memory answers 39/60 correctly versus full context's 46/60. It loses eight answers that full context gets right, and recovers one that full context misses. The invalid fine-grained labels prevent assigning all eight losses to a particular memory stage. BEAM-100K ties at 13/40, but has three memory-only wins and three full-only wins: equal aggregate accuracy does not mean identical information retention. Low full-context accuracy also signals answerer/task/rubric difficulty; retrieval fixes alone cannot promise high absolute accuracy.

## Prospective measurement protocol

1. **Define the claim.** Primary: memory preserves answer quality relative to full history when that exact history fits. A separate efficiency claim asks whether it saves product cost, context tokens or latency. A third track tests memory beyond the full-context window; truncated references there must stay labelled truncated. Keep that third track separate from full-context efficacy.
2. **Freeze a fitting, label-blind cohort.** Start with the 100 native-fitting BEAM-100K/LoCoMo development questions. For larger coverage, add independent conversations or a separately versioned LongMemEval-S development draw. Determine eligibility from the exact rendered source and model window before inspecting correctness or evidence labels. Retain chronology and all original source messages. Never create the primary baseline by retaining only gold sessions. If using smaller-history variants, select distractors/length by a documented outcome/label-blind rule and publish them as a separate transformed benchmark, not the original M suite.
3. **Verify actual fit.** Budget the entire serialized request: system prompt, roles/dates, schema overhead, question, and the declared 8,192 output tokens plus a safety margin. Use a validated tokenizer/count endpoint where available; verify actual reported wire input and no provider-side truncation. `len/4` and a context-window label alone are not proof. Preserve the complete-source hash, input message ids, removed count zero, input/output bounds and eligibility per question. An API/network failure is infrastructure, not a context-ineligible case or an incorrect answer.
4. **Compare full, incumbent and one candidate fix.** Same answer model revision, question, source history, decoding/reasoning settings, output and eight-turn budgets, judges and scoring templates. Full has the entire source and no memory retrieval. Incumbent/candidate have the same source-ingestion opportunity and prescribed memory budget. Two suites × three arms = **six development cells**, not another 25/75-cell sweep. This is a regression screen, not a claim that 100 questions have enough power for a 3-point non-inferiority conclusion. A fixed smaller smoke panel may debug ingestion first, but never becomes a selected favourable efficacy sample.
5. **Add diagnostic controls separately.** Full source; gold-evidence oracle; actual retrieved snippets; and an outcome-blind source view without memory where useful. Oracle labels are evaluator-only and cannot enter ordinary prompts. If an oracle fails, investigate answerer/prompt/judging before assuming more recall fixes it. On failed cases compare actual delivered evidence with what the full answer used; answer/source checks must be blinded and retained privately.
6. **Instrument the pipeline.** Count imported messages, eligible/refused/archived notes and source-id coverage. Record candidate pool/ranks, explicit query arguments, per-query recall and read hits, selected ids, delivered spans/excerpt hashes, required-evidence survival, repeat queries and remaining turn budget. Preserve private answers and checkpoint all-phase runs before judging; the existing all-phase path only caches answers for `--phase answer`, so the exact closed-run answer texts cannot all be causally rejudged. Source ids alone do not demonstrate fact visibility. Separate automatic passive lookups from explicit model tool calls.
7. **Report the right outcomes.** Per-suite binary and registered graded metrics, paired question wins/losses, fraction of full-correct questions retained by memory, retrieval recall-all at meaningful granularity, abstention and run-limit rates. Confidence intervals and randomization must respect conversation clusters and a predeclared multiple-comparison family. If choosing an exploratory non-inferiority margin (for example 3 percentage points), declare it before the new run; require the appropriate one-sided lower confidence bound to exceed the negative margin. Non-significance is not equivalence. Keep Task 18's existing acceptance rules unchanged. Use observed discordance and cluster variance to size an independent confirmation set; preregister the sample/stop rule rather than stopping when an interval looks favourable.
8. **Measure efficiency honestly.** Measure cold and warm cache separately; include product input/output/cache tokens, query latency and ingest/write time. Build each history once, freeze its store, then fork independent read-only answer branches so previous test answers cannot contaminate later questions. Report total cost and ingestion amortized over a declared number of questions per stored history. Current per-question temporary-store rebuilding does not measure production write-once/read-many economics. Missing usage is unavailable cost, not zero. Charge judges as evaluation, separately from product cost.
9. **Confirm rather than tune on the final test.** Development cases can diagnose/tune. A later locked, independent held-out cohort plus additional models is needed before general efficacy/default claims. Current owner closure remains intact; this proposal authorizes no paid rerun, new holdout access or default change.

Test-choice background: [Dror et al., ACL 2018](https://aclanthology.org/P18-1128/) and [multiple-dataset replicability analysis](https://arxiv.org/abs/1709.09500). Cohort format/evidence-session reference: [official LongMemEval repository](https://github.com/xiaowu0162/longmemeval). The specific budgets, cell count and proposed non-inferiority rule above are recommendations for this repo, not claims made by those papers.

## Does the existing plan already address the problems?

| Plan task | Relevance and recommended disposition |
|---|---|
| **5 — lexical enrichment, session/around navigation, query feedback** | Best first product step after measurement repairs. Directly targets partial/missing surfaced evidence without embeddings or a write-path model. Its per-query diagnostic already belongs in the plan, but it must distinguish candidate pool from rendered selection and include reads. |
| **6 — dates/timeline** | Already targets temporal questions. Evaluate on temporal strata with properly resolved dates; do not implement it because a generic “answer gap” label was high. Respect dependencies while doing 5–9. |
| **7 — current-state grouping** | Already targets stale/contradictory facts. Reassess with a correctly ingested conflict fixture; current MAB 0% is not evidence that the proposed grouping is inadequate or necessary. Keep its optional model wrapper separately costed. |
| **8 — precision-first passive delivery** | Direct match for noise/excerpt/token issues. Evaluate after correcting delivery metrics; blind confidence thresholds/pointer cards can hide useful evidence and worsen accuracy. Gate against incumbent on the fixed fitting cohort. |
| **9 — aggregation and abstention** | Direct match for multi-session completeness, counting, no-match signals and final synthesis. High priority with Task 5; group/page results and encourage bounded multi-query coverage before adding new architecture. |
| **10 — weaker tool-callers** | Some relevance to six run-limit failures, but this screen tested one model and fresh question sessions; it does not establish the proposed two-user-turn adaptation's efficacy. Preserve a final answer within the fixed budget and evaluate actual weak callers when authorized. |
| **11 — coding decisions** | Different domain. These conversational results do not justify prioritizing it as the remedy. |
| **12 — decision-model gates** | Optional extra model decisions/cost. Not needed to fix empty imports, bad metrics, or missing lexical navigation. Calibrate later against a repaired baseline. |
| **13 — typed-link association** | **Conditional after Tasks 5–9**, exactly as the plan states. The old screen flag is not sufficient to execute it now; candidate/selection labels are confounded. Implement only if properly measured residual multi-hop failures remain above its threshold. |
| **14 — safety** | Remains mandatory before promoting defaults. Retrieval improvements cannot bypass leakage, deletion, poisoning and false-refusal gates. |
| **15 — capacity/maintenance** | Important for scale and lifelong memory; not a proven cause of the current accuracy. Test real maintenance triggers and archive reachability before tuning capacity. |
| **16 — observational memory** | Separate memory path, unmeasured here. It cannot be inferred from this conversational exchange-only preset. Defer architectural choice until its own valid comparison. |
| **17 — fact extraction** | Explicitly conditional and adds write-path model cost. Keep deferred until read-time Tasks 5–9 fail on valid evidence and oracle tests show an irreducible representation problem. |

**Recommended sequence:** (A) repair ingestion/measurement/answer retention with offline regressions; (B) establish the fitting incumbent comparison; (C) implement Task 5 and reassess; (D) proceed through applicable Tasks 6–9 in dependency order, testing each change rather than bundling them; (E) run Task 13 or 17 only on measured residuals; (F) pass Task 14 and the unchanged independent acceptance gates before a default/preset promotion. Keep Task 15 as an explicit growth track. This uses the existing plan rather than replacing it with a new memory architecture.
